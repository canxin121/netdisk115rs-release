# v0.7.0：内置 MCP 服务端，让 AI 客户端直接驱动刮削与整理

本版给同一个二进制加了一个 [Model Context Protocol](https://modelcontextprotocol.io) 服务端，
把「媒体整理」这一整套能力暴露成 **41 个工具**，供 Claude Desktop、Claude Code 或任何说 MCP
的进程直接调用 —— 不再需要模型拼命令行、也不再需要人肉盯着串行执行。**默认只读**，写操作要
同时穿过四道闸才会落到 115。数据库 schema、媒体目录布局与前端不变。

## 两条传输，同一份实现

| 传输 | 入口 | 适合谁 | 鉴权 |
| --- | --- | --- | --- |
| stdio | `netdisk115rs mcp serve` | 本机桌面客户端（自己拉起子进程） | 无（进程本身即凭据边界） |
| Streamable HTTP | 现有服务上的 `POST /mcp` | 远程客户端、容器、共享服务 | 每端点一个 Bearer token + Host/Origin 校验 |

两条路共用同一个 `MediaMcpServer`：工具清单、`annotations` 与 `{state,data}` 信封逐字段一致。
集成测试会把两条传输的 `tools/list` 逐字段对比，防止悄悄漂移。唯一差异是 `nd115_fs_upload`
只在 stdio 下出现 —— 它读的是运行 MCP 的那台机器上的文件，而 HTTP 端点可能是公网可达的。

stdio 模式**不需要 HTTP 服务在跑，也不需要已登录 115**：只读工具与整个本地媒体库（SQLite）
在没有 115 会话时照样可用，真正要访问 115 的工具会在调用时返回
`{"state":false,"code":401,…}`。它也不会像服务进程那样在启动时把 `Running` 的计划改成
`Paused` —— stdio 是第二个进程，照做会凭空暂停一个正在健康运行的任务。

## 四道写操作闸门

默认 `allow_writes: false`。写操作要真的落到 115，必须同时穿过：

| 闸门 | 位置 | 失败时 |
| --- | --- | --- |
| `mcp.allow_writes` | 服务端配置 | 写工具**不出现在** `tools/list` 里 |
| `mcp.servers[].tools` 白名单 | 服务端配置 | 同上，不在白名单里就看不见 |
| `confirm: true` | 每次调用 | `isError` + 403 指引文案，**未发起任何请求** |
| 账号匹配 | 每次调用 | `account_id` 与端点绑定不一致 → 400 |

「不出现」而不是「出现但调不动」是刻意的：少一个被误调用的机会，模型的上下文里也不会出现
一个它其实用不了的工具。`confirm` / `dry_run` / `account_id` 是**控制字段而非业务参数** ——
它们不属于任何工具的输入 schema，但和业务参数一起平铺在 `arguments` 里，由服务端先剥离再
反序列化；放进 `arguments` 之外的层级等于没写，只会得到「缺 confirm」的 403。

写操作只接受**显式 `account_id` 或端点绑定的账号**，绝不回落到配置默认账号 —— 回落的代价是
「AI 在错的账号上整理文件」，比一个 400 贵得多。`nd115_plan_pause` / `nd115_plan_cancel` 是
唯一例外：它们标成只读，`allow_writes=false` 时依然可见、不需要 `confirm`，**出问题时必须还
能叫停**。

## 41 个工具

- **115 浏览（4，纯只读）**：`nd115_fs_ls` / `tree` / `stat` / `search`。`tree` 有硬上限
  （默认 3 层 / 2000 节点），超了显式标 `truncated`，不会偷偷截断；`search` 走 115 索引而非
  逐目录遍历。
- **媒体整理计划流水线（13）**：`nd115_plan_create` / `replace` / `get` / `list` / `delete` /
  `validate` / `preview` / `verify` / `run` / `resume` / `pause` / `cancel` / `events`。直接映射
  `src/library/plan.rs` 的既有函数，**不新增执行逻辑**。
- **规范化媒体库（18）**：读 `search` / `item_get` / `item_list` / `party_list` / `term_list` /
  `remote_search` / `sync_status`，写 item / party / credit / term / relation / collection
  member / `sync_run`。所有 update / delete **强制 `expected_revision`**，拿错 revision 会被
  409 拒绝 —— 这是防止覆盖别人改动的机制，AI 也不例外。
- **原生单步文件写（6，全部需 `confirm`）**：`nd115_fs_mkdir` / `move` / `copy` / `rename` /
  `delete` / `upload`。`move` / `copy` 走原生按父目录分组批量，一次请求一个父目录，而不是循环
  单条调用；`delete` **只进回收站**。

## 规范随二进制发布

三个 MCP **资源**用 `include_str!` 编译期嵌入，AI 读到的规范与当前这个二进制同版本，不依赖
部署目录里有没有 Markdown：

| URI | 内容 |
| --- | --- |
| `nd115://guide` | 执行指南 + `MEDIA_SCRAPING_CONVENTION.md` 全文 |
| `nd115://guide/scraping` | 刮削与便携 Sidecar 规范 |
| `nd115://guide/library` | 规范化媒体库（`MEDIA_LIBRARY.md` 提要） |

`initialize` 的 `instructions` 里另带一段纪律摘要（Plan 是默认路径、绝不猜测路径和 ID、写操作
先 `dry_run`、遇冲突停下报告），客户端即使不读资源也知道红线在哪。
`MEDIA_SCRAPING_CONVENTION.md` 新增 §13.1，写明 MCP 是既有阶段 A–D 流水线的等价路径。

## 刻意没有的能力

以下能力**不存在，也不会因为改配置而出现**：永久删除 / 清空回收站 / `delete_secret`；登录、
改 Web 访问密码、增删 115 账号；写服务端配置（`POST /api/config`）；WebDAV / File Provider 的
token 与挂载配置写入；回收站安全密码（`verify_pass`）；直链与分享票据签发（描述符里给的是
**永久路径 URL**，满足规范 §2「不把登录态、Cookie、下载直链、临时签名 URL 写入文件」）；把
文件下载到运行 MCP 的机器上。

## 顺带的整理

散落在 `file_provider_api` / `webdav` / MCP 的三份 `constant_time_eq` 收敛成 `src/access.rs`
的一份共用实现（纯去重，行为不变）；File Provider 的并发播放会话上限
（`MAX_PLAYBACK_SESSIONS`）从 64 提到 4096 —— 原值对多播放器/多设备同时在线过紧，
超出后按创建时间淘汰最旧会话，会让正在播放的客户端被换掉票据；
`media_tickets_are_random_bounded_and_grouped_by_native_batch_limit`
里一条既有的断言被修正为与 `fa6d8a3` 引入的七天票据寿命一致（原断言在 HEAD 上即失败，
与本版无关），并补了一条对照组断言。`create_plan` / `replace_plan` 的入库前校验在本轮之前
就已存在，本版未改动。

## 配置

新增 `mcp:` 段，默认关闭（旧配置照常解析，`CONFIG_VERSION` 不变）：

```yaml
mcp:
  enabled: false
  allow_writes: false
  default_account_id: ""
  servers: []            # 见 config.example.yaml 的带注释示例
```

没有配置任何启用的 server 时 **`/mcp` 路由根本不注册** —— `POST /mcp` 会落到静态服务返回 405。
这比注册一个永远 503 的路由干净：探测者拿不到任何「本机配了 MCP」的信号。token 由
`Config::validate()` 强制至少 24 个可打印 ASCII 字节，启用端点之间不能复用；空 token 永远不是
「开门」，而是**配置加载失败**。

## 升级与验证

本版不迁移数据库 schema，不改前端资源，不清空索引、媒体库或云盘数据；建议升级前备份配置与
数据目录，再用既有安装器升级。MCP 默认关闭，升级后行为与 v0.6.0 一致，需要时再在配置里打开。

发布候选在本提交上通过以下检查：

- `cargo test --locked` 全绿（含 15 项 `tests/mcp_routes.rs`：路由未注册时 POST 405 / GET 404、
  401/403 鉴权与 `WWW-Authenticate`、`tools/list` 的写工具可见性随 `allow_writes` 开关切换、
  端点白名单收窄、缺 `confirm` 的写调用**未发起任何请求**、跨账号写 400、`dry_run` 预演、
  资源读取、以及唯一一项真实子进程测试 —— 起 `mcp serve` 断言 stdout 上只有 JSON-RPC）。
- `cargo build --locked` 仅剩两项既有警告（`src/routes/media.rs`、`src/file_provider_api.rs`），
  在本版中未新增。
- 手工以 Claude Code 各接一次：stdio（`claude mcp add`）与 `POST /mcp`（Bearer token），各跑
  `tools/list`、一次只读调用、一次不带 `confirm` 的写调用（返回 403 指引）与一次
  `fs_mkdir` 的 `dry_run` 预演。

## 兼容性

- 未开启 `mcp.enabled` 时，路由、CLI 子命令与运行期行为与 v0.6.0 完全一致（`mcp serve` 会明确
  报「MCP 未启用」而不是静默退出）。
- 数据库 schema、媒体库索引、媒体目录布局契约、WebDAV 与 `web/` 前端均不变。
- `library plan create` / `POST /api/library/plans` 收紧为入库前校验：此前"先存后爆"的错误输入
  现在立刻 400。合法输入不受影响。

配置与客户端接入（Claude Desktop / Claude Code JSON、`claude mcp add`、token 生成、公网暴露
前提、排障表）见 **`docs/MCP.md`**。
